# Механизм эмуляции платежа — кейс 3 
## 1 Состояния платежа
* CREATED — платёж создан, суммы зафиксированы, QR зарезервирован; подтверждение ещё не отправлено шлюзу.
* PENDING — клиент подтвердил, запрос обрабатывается или результат неизвестен после таймаута.
* SUCCESS — получено подтверждение успеха; QR окончательно использован.
* DECLINED — получен явный отказ; списания в эмуляторе нет, резерв QR освобождён.
* CANCELED — клиент отменил CREATED до начала обработки; резерв освобождён.

## 2. Матрица переходов
|Из состояния|В состояние|Условие|
|-|-|-|
|CREATED|PENDING|Владелец сессии подтвердил платёж; статус меняется до вызова шлюза|
|PENDING|SUCCESS|h от 0 до 7 включительно|
|PENDING|DECLINED|h=8; CARD_DECLINED, HTTP 402|
|PENDING|PENDING|h=9; GATEWAY_TIMEOUT, HTTP 202; результат неизвестен|
|CREATED|CANCELED|Клиент отменил до подтверждения|
|PENDING|CANCELED|Запрещён; CANCEL_NOT_ALLOWED, HTTP 409|
|SUCCESS|CANCELED|Запрещён; CANCEL_NOT_ALLOWED, HTTP 409; возврат вне задания|

## 3. Шаги обработки платежа
| Шаг | Проверки и действие | При ошибке |
|---|---|---|
| 1. Валидация и повтор | Проверить формат, обязательные поля, доступ сессии; найти ключ. При совпадении ключа и тела вернуть существующий платёж | VALIDATION_ERROR (422); изменённое тело с тем же ключом — IDEMPOTENCY_CONFLICT (409) |
| 2. Проверка QR | Наличие QR, HMAC, exp, ACTIVE-мерчант, сотрудник того же ресторана, совпадение receipt_id, свободный nonce | INVALID_QR, QR_EXPIRED, MERCHANT_BLOCKED, MERCHANT_NOT_ACTIVE, RECEIPT_MISMATCH или QR_USED; платёж не создаётся |
| 3. Расчёт | Decimal, 0 < base ≤ 1 000 000, 0 ≤ pct ≤ 50, итог ≤ 2 000 000 | AMOUNT_OUT_OF_RANGE либо TIP_OUT_OF_RANGE (422) |
| 4. Создание | В одной операции создать уникальный payment_id, CREATED, связь с QR и ключом, зарезервировать QR; вернуть 201 | При конкурирующем резерве QR_USED (409); при сбое хранения INTERNAL_ERROR (500), без частичной записи |
| 5. Подтверждение | Проверить владельца, токен и CREATED; перевести в PENDING, вызвать шлюз один раз | Ошибка токена — FORBIDDEN (403); повтор подтверждения возвращает текущий статус; конфликт перехода — INVALID_PAYMENT_STATE (409) |
| 6. Результат | По h сохранить SUCCESS / DECLINED / PENDING; показать суммы и код результата | Таймаут не считать отказом; резерв сохраняется; при сбое записи результат не объявлять окончательным |
| 7. Отмена | До подтверждения перевести CREATED в CANCELED и освободить резерв | Из остальных состояний CANCEL_NOT_ALLOWED (409), без изменения статуса |
| 8. Аудит | Каждое действие записать вместе с изменением состояния; исключить секреты и реквизиты | При невозможности согласованной записи не подтверждать успешность операции; INTERNAL_ERROR, проверить состояние по тому же ключу |

## 4. Формулы
- `tip_amount = ROUND_HALF_UP(base_amount × tip_pct / 100, 2)`.
- `amount_total = base_amount + tip_amount`.
- `h = int(MD5(UTF8(qr_id + nonce)).hexdigest(), 16) % 10`.
- `payload = merchant_id + "|" + employee_id + "|" + receipt_id + "|" + nonce + "|" + exp`.
- `SIGNATURE = HMAC_SHA256(SECRET, UTF8(payload)).hexdigest()[:16]`.

## 7. Обработка ошибок
| Ситуация | error_code | HTTP | retryable |
|---|---|---|---|
| QR signature не совпала | INVALID_QR | 422 | нет |
| QR истёк | QR_EXPIRED | 410 | да, только с новым QR |
| nonce использован | QR_USED | 409 | нет для нового платежа по этому QR; запросить статус существующего |
| merchant BLOCKED | MERCHANT_BLOCKED | 403 | нет |
| tip_pct > 50 | TIP_OUT_OF_RANGE | 422 | нет без исправления |
| amount_total > 2 000 000 | AMOUNT_OUT_OF_RANGE | 422 | нет без исправления |
| Тот же idempotency_key | отсутствует | 200 | повтор безопасен, возвращается существующий платёж |
| Эмулятор вернул 8 | CARD_DECLINED | 402 | нет для той же попытки; новая попытка возможна после отказа |
| Эмулятор вернул 9 | GATEWAY_TIMEOUT | 202 | да, проверка статуса того же платежа |
| Отмена из PENDING | CANCEL_NOT_ALLOWED | 409 | нет |
| Отмена из SUCCESS | CANCEL_NOT_ALLOWED | 409 | нет |

## 8. Идемпотентность
Ключ означает «это тот же запрос», хранится вместе с идентификатором клиентской сессии, параметрами и payment_id. Первый запрос создаёт одну запись (201); повтор с тем же содержимым возвращает тот же платёж (200). Повтор проверяется раньше занятости nonce. Другие параметры с прежним ключом — 409 IDEMPOTENCY_CONFLICT.

В выходном хранилище одна запись на payment_id, её статус обновляется. Входной payments.csv содержит 100 исторических записей и не меняется. Проектные ключи, QR-связи и резервы требуют отдельного служебного хранения: семи колонок CSV недостаточно. Конкурирующие запросы должны проверяться атомарно; простого append для этой гарантии недостаточно.
